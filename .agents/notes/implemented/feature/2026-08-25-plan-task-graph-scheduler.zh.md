# Agent Note：Plan 任务图调度

Status: implemented

[English](2026-08-25-plan-task-graph-scheduler.md) | 中文

## 问题

Plan mode 之前只记录协作模式开关。需要执行多个独立规划步骤的调用方没有共享的依赖调度器、持久任务状态，也没有一致的失败和取消结果。

## 决策

`PlanModeController.execute()` 接受带品牌的 plan id、有序任务图和 host executor。纯调度器会在启动任何任务前校验图，只准入依赖已完成的任务，并按输入顺序提交无冲突批次。任务默认是 `exclusive`；资源键相交的 `parallel` 任务不会进入同一批。`maxParallelTasks` 是部署配置，默认值为 `10`。

每个已准入任务会收到共享取消信号以及已完成依赖输出的只读映射。executor 失败会变为 `failed`，后继任务变为 `blocked`，无关任务继续执行。取消会停止新任务启动并等待已准入 executor 结算。由于任意 executor 输出不是持久 JSON 契约，任务输出只保留在进程内。

会话日志通过 `plan/tasks`、`plan/task-status` 和 `plan/end` 记录初始图、每次状态转换以及最终结果。`foldPlanExecution()` 可以重建有序的持久状态。这些事件只存在于日志中，不会进入模型历史。

## 验证

确定性调度器测试覆盖依赖、有界批次、失败隔离、blocked 传播、取消、重复执行防止、结果顺序、图校验和资源冲突。Plan mode 集成测试覆盖持久状态转换和回放折叠。持久化目录和 Cordis catalog 均从声明生成。

## 曾考虑的替代方案

**只串行执行：** 否决，因为独立任务无法使用调度器的有界并行能力，配置的批次上限也失去意义。

**从任务描述推断冲突：** 否决，因为描述不能可靠声明读写关系；调用方必须显式提供资源键。

**进程崩溃后自动恢复未完成任务：** 否决，因为任意 executor 状态不会持久化，自动恢复可能在缺少所有权或幂等保证时重复副作用。

## 后果

调度器无法从任务描述推断读写安全性；调用方必须声明 `parallel` 和资源键，未声明并发性时保持 fail-closed。进程崩溃会在日志中保留最后一个已提交状态，不会自动恢复未完成的任务图。
